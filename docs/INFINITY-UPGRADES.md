## 0. 先把这段曲线的形状钉死（实测数据）

> **改参数只跑数学模型**：`node tools/pace-model.mjs`（形状对照 / 起点与速率阶梯 / 到打破无限的时间），
> `--sweep` 给 R₀ × D 矩阵，`--check` 是 6 条与沙盒实测对齐的定点断言（0.9% / 4.7% / 0.4%）。
> 只有数学模型说不清的问题（例如多层反馈环）才回去跑 `infinity-sim.mjs`。

| 事实 | 数据 | 来源 |
|---|---|---|
| 解锁量子层（`peakMatter ≥ 1e25`）那一刻手里已有 **10 个量子** | R = 0.0476 阶/秒 = 上限 0.05 的 **95.2%** | `node _probe-*.mjs` 实测（见 0.5.0 前的设计讨论） |
| 这段的爬升全靠量子项，**a区 产率升级对它无效** | 基础环比指数项小 **1e200 倍** | 同上；也解释「熵阱价格 ×10 只让熵阱少一半、斜率一字不变」 |
| 整段耗时 = (308.2547 − 起始阶数) ÷ R_eff，且 `R_eff ≤ growthRateMax` | 基线 283.25 阶 @0.0488 ≈ **96.7 分钟**（+ 前置 6 分钟） | `tools/headless.mjs` / `tools/infinity-sim.mjs` |

**由此得到一条硬结论**：这段曲线只有 **两个** 真杠杆 ——

- **L1 抬 `R` 的上限**（`QUANTUM.growthRateMax`）
- **L2 缩短距离**（抬高起始深度 / 降低解锁门槛）

「让 R 更快饱和」（给量子、降捕获门槛）**几乎没收益** —— 因为解锁瞬间 R 已经吃到 95%。

### 各手段能省多少（算好的）

| 手段 | 到 e308.2547 的用时 | 相对基线 |
|---|---|---|
| 基线：起始 1e25，R=0.0488 | 96.7 分钟 | — |
| **L1** R → 0.055 / 0.06 / 0.07 / 0.08 / 0.1 | 85.8 / 78.7 / 67.4 / 59.0 / 47.2 分钟 | −11% / −19% / −30% / −39% / −51% |
| **L2** 起始 → 1e50 / 1e100 / 1e200 / 1e280 | 88.2 / 71.1 / 37.0 / **9.6 分钟** | −9% / −26% / −62% / **−90%** |

> L2 的曲线很"钝"：抬到 1e100 只省 26%，**必须抬到 1e200 以上才质变**。

## 3. 结论与建议

### 3.1 路线 1（爬升形状变 log）—— **已落地**

现状曾是 (t, `log10 物质`) 上的**直线**（斜率恒为 R）。要让曲线弯，只能让 R 随深度递减。
沙盒实测（`_sim/route1.mjs`，D=100、knee=25、R₀=0.147）：

| 每 25 阶耗时 | 改之前（直线） | 现在（log 形） |
|---|---|---|
| 25→50 | 6.7 min | **2.9 / 3.1 min** |
| 100→125 | 8.8 | 5.6 / 5.2 |
| 175→200 | 8.8 | 9.2 / 8.8 |
| 250→275 | 8.8 | 15.3 / 14.7 |
| **e25→e308.25 合计** | **97.6 min** | **105.1 / 100.2 min** |

（沙盒 / 数学模型两个数；差 ~5 分钟是每轮开头 ZPE 与量子的爬坡余量，已标定进模型。）

**knee 对照（解析式，已用沙盒校准，误差 <5%）**：

| knee | 维持 100 分钟所需 R₀ | 形状 | 起点跃迁到 1e200 后单次 | 节省 |
|---|---|---|---|---|
| **25（选定）** | **0.147** | 全程凹（每 25 阶单调递增） | 61.4 min | −39% |
| 50 | 0.124 | 前 25 阶直线 | 61.2 min | −39% |
| 100 | 0.090 | 前 75 阶直线 | 59.5 min | −40% |
| 200 | 0.056 | 前 175 阶直线（曲棍球杆） | 47.9 min | −52% |

⇒ **选 knee = 25**：与 50/100 的"起点跃迁收益"完全相同（−39%~−40%），但形状全程在弯；
只有 200 才让起点跃迁更强，代价是前 175 阶又变回直线（正是要避免的东西）。

**已落地的三个量**（必须一起改，否则总时长会漂）：
`config.js` 的 `CLIMB = { knee: 25, halvingOrders: 100 }`、`QUANTUM.growthRateMax = 0.147`、
`formulas.js` 的 `climbFactor()`（并与 `tick` 共用 → 显示 == 实际）。

### 3.2 ④ 的耗时上限 —— **已落地（1800 秒）**

`INFINITY_UPGRADES.ipTime.capSeconds = 1800`（30 分钟）。
`IP/小时 = 60 × 3^① × min(T,1800)/T`：单次 ≤30 分钟吃满，100 分钟只拿 30%。
沙盒实测代价很小（打破无限 4.1h → 4.8h），但它让"速度"有了意义。
数值不敏感 —— 想改就改 `capSeconds`，然后跑 `npm run pace` 复算（模型会吃这个常数，
`--check` 里有断言防脱节）。

### 3.3 原始 16 格提案（保留备查）

1. **只想加速 1e25→1e308.25 的话，16 条里真正有用的是第 1、2 排的前 4 条中的 4~6 条**：
   第 1 排 4 条 + 第 2 排 4 条 = 8 条就能把这段从 ~97 分钟压到 **10 分钟以内**（R+0.04 & 起点 1e280）。
2. **其余 8 条里有一半是结构性无效的**（给产率、给量子），原因见第 0 节：R 已饱和 + 基础环小 1e200 倍。
   把它们做出来只会让玩家觉得"买了没感觉"。
3. 所以建议的路线是：
   - **先做 4 条**：`速率解放 I/II` + `起点跃迁 I/II`（价格沿用 AD 的 10/100/20/40），一段从 97 分钟 → ~63 分钟；
   - 再把 `III/IV` 作为"打破无限之后"的长期目标（那时玩家有稳定的 IP 收入）；
   - **剩下的格子留给 ∞ 之后的层**（过载拐点、量子经济、零点能引擎）—— 那些才是能让数字继续长的地方。
4. 若坚持要 16 条齐活：按上表实现即可，但请在 UI 里对 ✗ 类条目写清楚它的作用范围（例如"对 1e25→e308 段无效，但它抬过载拐点"），否则就是自己骗自己。

## 4. 实现时的硬约束（本项目已有自检会拦）

- 改 `R` 上限 → 必须重跑 `tools/headless.mjs`（S 判据）与 `tools/infinity-sim.mjs`（节奏）；

- 任何新升级的效果文本必须从公式推导（`infinityUpgradeEffect()` 那种写法），**不许手写字符串**；
- 每加一条，都要在 `tools/infinity-sim.mjs --check` 里补一条定点断言。
