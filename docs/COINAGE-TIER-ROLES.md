# 铸币 / 档位的重新定位（方案A · 设计稿）

> 状态：**仅设计，未动代码** ✓
> 目的：让「铸币」与「档位」各自拥有**不可替代的玩法位置**，而不是与别的机制抢同一个职能。
> 结论预告：**档位留作「节奏脊柱」**（它已承重 ✓），**铸币改造成「量子 → 无限点」的转换器** ✓。

---

## 0. 一句话

```
现在：铸币 = 又一个 IP 乘数 ✗（与 ipDouble、深度复利 抢活 ✗）
      档位 = 上限 + rate + 润滑 三件事一起管 ✗（职责过载 ✗）
方案A：档位 = **节奏脊柱**（只管"每轮大坍缩有多快"✓，即 tierAccel）
       铸币 = **量子 → 无限点**（把量子的产出接进 ∞ 层 ✓，与"余额→收益"的 ipDouble 分工明确 ✓）
```

## 2. 真正的问题：**职能重叠** ✗（不是"多余" ✗）

```
IP 的四个来源，全都在做"把某个东西乘以一个大数"：
  ① 深度复利    10^(0.0035 · 超出阶数)      ← 来自"挖多深" ✓
  ② ipDouble    ×2^等级                      ← 来自"余额" ✗（余额越大收益越大 ⇒ 与①重叠 ✗）
  ③ 铸币        ×coinageMult                 ← 来自"铸币等级" ✗（也是纯乘数 ⇒ 与②重叠 ✗）
  ④ 量子铸币    ×f(量子)                     ← 来自"量子" ✓（职能最独特 ✓）
⇒ ②③ 只是"另一条乘数"✗ ⇒ 玩家看不出它们的区别 ✗（这正是你觉得它们可疑的原因 ✓）
```

## 3. 方案A：分工

### 3.1 档位 = 节奏脊柱（**不改职能，只明确边界**）

```
保留：tierAccel（每档 ×1.40）✓ —— 它是"每轮大坍缩有多快"的唯一总闸 ✓
保留：cap（铸币上限）—— 但上限的**依据**改为"本档进度"而不是"大坍缩次数"（见 3.2 ✓）
保留：lube（量子润滑）✓ —— 它管量子阶梯，与节奏正交 ✓
移出：`rate` 那一项 ✗（它和 `b` 的其它来源重叠 ✗）⇒ 并入 tierAccel ✓
⇒ 档位的对外语义收敛为一句：**"我决定你下一轮要跑多久"** ✓
```

### 3.2 铸币 = 量子 → 无限点（**换职能**）

```
现在：铸币等级 → coinageMult（纯乘数）✗
方案A：铸币等级 → **把「本轮量子的产出」按比例转成无限点** ✓

  建议形式（单轮结算时）：
      ΔIP = quantumThisRun × coinageRate(等级)
      其中 quantumThisRun = 本轮捕获的量子对数 × 每对量子（2 或 3 ✓）

  为什么这样分工才对：
    · 量子是**本轮归零**的量 ✓ ⇒ 它天然是"每轮重来一次"的资源 ✓
    · IP 是**跨轮累积**的量 ✓ ⇒ "每轮把量子兑换成 IP" 是**唯一**由量子驱动 IP 的入口 ✓
    · 与 ipDouble（余额→收益 ✗）**完全不重叠** ✓：一个吃"存量余额"，一个吃"本轮产出" ✓
```

**乘区归属**（按项目规矩：只看加成位置 ✓）：

| 项 | 落点乘区 | 理由 |
|---|---|---|
| 铸币的兑换率 | **IP（∞ 层）** ✓ | 产出的是无限点 ✓（与 `ipFromQuantum` 同类 ⇒ 应合并或明确二选一 ✓） |
| 档位 `tierAccel` | **粒子（`b`）** ✓ | 它改的是"+粒子获得的时变增幅速率" ✓（已在代码里如此 ✓） |

### 3.3 数值与软上限（**必须遵守的判据**）

```
判据（这几轮反复验证过的 ✓）：任何"数量 → 加成"的映射，
   若对 x（超出上限的阶数）是**指数** ⇒ 有限时间爆炸 ✗
   是**多项式**（线性 / 开根）⇒ 安全 ✓（∫ 发散 ✓）

⇒ 铸币的兑换率建议：`coinageRate = cMul × √铸币等级` 或 `加法区 +等级` ✓（**不要** `×2^等级` ✗）
⇒ 档位 tierAccel 是"每档常乘数"✓ ⇒ 它按**次数**累积 ⇒ 次数受"每轮时长"约束 ✓ ⇒ 天然安全 ✓
   （但次数若随深度暴涨 ⇒ 要按 `post-break-runaway-lab` 检查 ✓）

软上限（用户既有要求：影响永恒的东西必须有极强软上限 ✓）：
   · 铸币的 `coinageRate` 走**阈值软上限**（`knee + 超出·2^(−超出/跨度)` ✓ 与现有一族同形 ✓）
   · 档位的 `tierAccel` 保持"每档常乘数"，但**档数上限**由 `cap` 与 lube 共同约束 ✓
```

## 附：判据速查（这几轮总结的，写给未来的自己）

```
1. 任何"数量 → 加成"若是**指数**（2^n / 10^n / effectMult^n）⇒ 有限时间爆炸 ✗
   判据：∫dx / FORM(x) 收敛 ⇔ 爆炸 ✗
2. 只有**多项式**（线性 / 开根）安全 ✓（∫ 发散 ✓）
3. "除数"只能救**已经是对数/线性**的量 ✓；对指数量的除数**无效** ✗（IP/D 仍是指数 ✗）
4. 乘法增幅（×effectMult^等级）只要 `costMult > effectMult` 就不是自持爆炸 ✓，
   但会让"余额越大、单轮收益越大"⇒ 把时长压得很短 ✗（需配合延长单轮 ✓）
```
