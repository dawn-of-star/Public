## 0.1 ★★★ 开发主旨（用户 2026 通知，**统领整个系统**）

> 用户原话：「ad 中**时间研究与永恒挑战贯穿了永恒前期与中期**，
>   我们对标的**七巧板与七巧板拼图挑战也应该同理**」

**对标关系（三件事一一对应）**：

| AD | 我们 | 共同点 |
|---|---|---|
| **时间研究树**（花 TT） | **七巧板**（花 EP） | 从永恒**前期**开始逐个解锁，一路延伸到中期 |
| **永恒挑战**（EC1~EC12） | **拼装挑战** | 同样贯穿前期→中期，且同时是**门禁 + 奖励** |
| 单个**晚期**节点（如 TS181 需 `TS171 + EC1~3`、200 TT） | 单个晚期奖励（如"每秒 IP"） | **节点可以晚，但系统本身不许只在晚期** ✓ |

⚠️ **⚠️ 我先前的一处误导**：我查 AD 源码时发现 TS181 发放很晚（`TS171 + EC1/EC2/EC3`、200 TT），
于是建议"这条奖励的时机应偏晚" —— 那只对**那一个节点**成立；
**整棵树的跨度是"前期→中期"** ⇒ 本主旨把它纠正过来 ✓

### 由此得出的硬要求（实现时必须满足，否则主旨没兑现）

1. **巧板必须能"一个一个、从早期就开始"拿到**（概率获取 + 保底）—— 不能攒齐才生效
2. **覆盖率本身就是那条斜坡**：`cov ∈ [0,1]` ⇒ 前期盖一点点、中期盖大半
   - ⇒ 三条轴的**终态值**（10000 级 / 1e13 / 5000%）是"**盖满**"时的上限，
     而收益**随覆盖率连续增长** ⇒ 天然贯穿前期与中期 ✓
   - ⇒ **映射形式建议几何插值**：`轴值(cov) = lo × (hi / lo)^cov`
     （`cov=0 ⇒ lo`、`cov=1 ⇒ hi`；连续、单调、且与"覆盖比例给加成"的字面一致 ✓）
3. **拼装挑战要分层**：低难度挑战**前期就能打**（对应 EC 的早期关卡），高难度留到中期
4. ⚠️ **反例（不许）**：把三条轴做成"集齐 7 块才给全额"的**开关** ✗ ——
   那就退化成"一个晚期节点"，主旨当场落空

## 1. 几何（用户 2026 澄清，**这是实现的核心**）

最终目标是**把七块板拼成一个正方形**（经典七巧板）。取正方形**左下角为原点**，
只看**三条线**：

| 轴 | 是哪条线 | 加成随什么走 |
|---|---|---|
| **纵轴** | **左边缘**（左下 → 左上） | 该线被板块**占据的比例** |
| **横轴** | **下边缘**（左下 → 右下） | 同上 |
| **斜轴** | **左下 → 右上 的主对角线** | 同上 |

- **「边、点、面覆盖都算」**（用户原话）⇒ 判定是"这条线上被盖住的部分"，不要求整边对齐
- ⇒ **整个机制可以归约成三个百分比** `cov纵 / cov横 / cov斜 ∈ [0, 1]` ✓
  （不需要多边形布尔运算那套重东西 —— 只要：块体的边**吸附**到网格后，
  求三根线上被覆盖线段的**并集长度 / 总线长**）

## 5. ⚠️ 必须先解决的三件事（阻塞实现）

### 5.1 「每秒获得本次无限可获得的 IP 点」= **AD TS181 的同类**（已核到源码）

**AD 的原文与实现**（用户 2026 提供本地源码：`D:\game\AntimatterDimensionsSourceCode`）：

```js
// src/core/secret-formula/eternity/time-studies/normal-time-studies.js:426~436
{ id: 181, cost: 200,
  requirement: [171, EC1完成, EC2完成, EC3完成], reqType: ALL,
  description: () => `You gain ${formatPercents(0.01)} of your Infinity Points gained on crunch each second`,
  effect: () => gainedInfinityPoints().times(Time.deltaTime / 100)... }
```
- `Time.deltaTime` 的单位是**秒**（`src/core/time.js:47` 的 `totalSeconds`）⇒
  **效果 = 每秒获得「本次大坍缩所获 IP」的 1%** ✓（与描述一致，不是 10%）
- 前置 `TS171 + EC1/EC2/EC3`、成本 **200 TT** ⇒ **发放很晚** ✓
- 效果还乘了一个 Reality 升级的口子（`continuousTTBoost…autoPrestige`）⇒ **AD 留了后续放大位** ✓

**推论：AD 的 1% 是"涓流"，不是"替代"** —— 100 秒才等于一次大坍缩，
所以它不取代"手动大坍缩"这个动作。

### 5.1b ⚠️ 但"100% 会不会 runaway"——**系数与安全性无关**（我先前说错了一半）

用户原话说"我认为及其安全，参考 ad TS181"。核完源码后，**这是对的**，理由是数学的：

```
dIP/dt = c · IP^p        ⇒ 有限时间爆炸 ⟺ p > 1        （**与系数 c 无关**）
```
- `c` 只改**快慢**，不改**会不会爆** ⇒ 「1%/秒」与「100%/秒」**同为亚临界或同为爆炸** ✓
- 直接自环（`ipDoubleMult = 2^等级`、浅段价格每级 ×10 ⇒ 池 P 买得起 `L ≈ log10 P`）：
  `G ∝ 2^(log10 P) = P^0.301` ⇒ **`p = 0.301 ≪ 1`** ✓ 余量很大
- ⇒ 所以 AD 那条 1% **不是因为"1% 够小才安全"**，而是因为 `p < 1` ✓

**⇒ 结论改写**：这条的争论**不是安全问题，是平衡问题** ✗
- 对齐 AD ⇒ 系数取 **`0.01`**
- 要字面的 100% ⇒ 那是**平衡选择**（代价：生效期间大坍缩失去意义，因为被动比手动快约 35 倍）
- ⚠️ 仍需补的一步：全环指数不能只看 `ipDouble`（`IP → ∞升级 → 深度 → 深度收益 → IP` 也在环里）。
  余量虽大（0.301 vs 1），但按项目规矩应把全环 `p` 算出来再签（工具：`tools/ip-economy-lab.mjs`）

### 5.2 三条轴的**软上限**（用户自己的既定规矩）

`PROGRESSION.md` §4.5：「影响永恒阶段的量必须有**极强软上限**（分轴价格段 / 效果硬封顶，二选一）」⇒
三条轴都直接喂**永恒阶段**（引擎 / 熵→粒子 / 计数频率）⇒ 三条**各需一个上限** ✓
⚠️ 其中**斜轴是唯一"仿射且与等级线性"**的（引擎两条是 √/饱和）：`1 + 等级×系数`，
系数推到 50 时，等级一高就是线性膨胀 ⇒ **它最需要封顶** ✗

### 5.3 板图：**按"经典方形七巧板"开发**（用户 2026 裁定）

用户原话：「我只能说相当自由，只能按照描述而言（如果你是要**绝对精确**的提示的话，
请**按照方形的七巧板**开发）」

⇒ 勘定：**取标准七巧板**（能拼成正方形的那个经典 7 块），把正方形当作 **4×4 的整数网格**
（边长 = 4 单位），则七块板的顶点**全部落在整数坐标上**，尺寸也随之确定：

| 块 | 形状 | 尺寸（正方形边长 4） | 面积占比 |
|---|---|---|---|
| 大三角 ×2 | 等腰直角 | 直角边 **2√2** | 各 **1/4** |
| 中三角 ×1 | 等腰直角 | 直角边 **2** | **1/8** |
| 小三角 ×2 | 等腰直角 | 直角边 **√2** | 各 **1/16** |
| 正方形 ×1 | 正方形 | 边 **√2** | **1/8** |
| 平行四边形 ×1 | 平行四边形 | 底 **2** × 高 **1** | **1/8** |

（面积校验：`¼+¼+⅛+1/16+1/16+⅛+⅛ = 1` ✓）

- 「**相当自由**」⇒ 拼装**不是固定插槽**：板块可 `R` 旋转 / `F` 翻转，落点靠**边缘吸附 + 顶点吸附**，
  三条线的覆盖率 = **已放置板块与那三根线的重叠并集 / 该线全长** ✓
- 三条线（左下角为原点）：**左边缘** `x=0` ｜ **下边缘** `y=0` ｜ **主对角线** `y=x`（`0 ≤ x ≤ 4`）
- ⇒ 用整数网格 + "线段并集"就能算，**不需要多边形布尔运算** ✓

panel-tangram

**坐标系约定**：原点 = 正方形**左下角**；SVG 的 y 轴向下 ⇒ 左下 = `(0,100)` ✓
三条轴：左边缘 `x=0`（`(0,100)→(0,0)`）｜下边缘 `y=100`｜主对角线 `(0,100)→(100,0)` ✓

**守卫**（`tools/dom-smoke.mjs` 的「标签子页」块）：钉住五件事 ——
① CSS 右列**真的是 `15%`**｜② **坐标轴名义尺寸 ≥ 760px**（用户要的 5 倍；不写死 950，因为他说的是"差不多"）
｜③ **没有假装有覆盖率**（三条轴的 `stroke-dashoffset` 仍等于各自全长 `100/100/141.42` ⇒ 完全不可见）
｜④ 三条轴**都在**（`tg-cov-*` = 3/3）＋ 托盘**七个槽位** ＋ 拼装挑战节存在 ✓
⚠️ **只断言结构，不断言覆盖率数值**（机制未实现 ⇒ 没有真值可断 ✗）
✅ 已做**反向测试**（三次都当场红，且诊断精确到哪一项挂了；每次都用哈希校验**字节精确**还原）：
`15% → 20%` ⇒ `右列15%=false`｜`950px → 190px` ⇒ `坐标轴=0px`｜`dashoffset 141.42 → 70` ⇒ `无假覆盖率=false` ✓
（"能过的守卫不代表会红"—— 项目那条假绿教训）

⚠️ **尺寸与线宽是耦合的**（踩过后写下来）：`stroke-width` 是 **viewBox 单位** ⇒ SVG 放大 5 倍线就粗 5 倍 ✗
⇒ 线宽必须同步缩 5 倍（`tg-frame 0.8→0.16`｜`tg-axis 2→0.4`｜`tg-cov 2.6→0.52`）才能保持屏幕上的粗细不变。
⚠️ **不能用 `vector-effect: non-scaling-stroke` 图省事** —— 它会把 `stroke-dasharray` 也变成屏幕像素
⇒ 覆盖率高亮的 dash 数学（全长 100 / 141.42）会**算错** ✗
