## 1. 定位（这条先定，其他都好办）

- **乘区**：梦想系统 → **虹色（dream zone）**。若它的某些效果落在别处（例如"自动化引擎等级"），
  那些效果按**落点**上色（ZPE 蓝 / 价格灰…），而 neko 卡片本身仍是虹色。
- **货币**：梦想点（`state.dreamPoints`）。它是"成就货币、永不重置"，正好适合当**元系统**的钱。
- **一句话定位**：**neko 是"替玩家干活"的一层** —— 现有 4 条梦想升级是"自动化某个具体升级"，
  neko 是"自动化那些自动化"，并且把梦想点从"一次性解锁"变成"可持续成长"。

## 2. 为什么不跟现有 4 条梦想升级重复

现有 4 条（`autoPhase` / `autoVacuum` / `autoDeGainBase` / `autoConvOutput`）都是**一次性**：
买断 → 某个暗能量升级自动购买。它们没有等级，也没有"选择"。
neko 如果只是"再多几条自动购买"，就是重复劳动。所以草稿把 neko 放在**它们之上**：

| 层级 | 现有 | neko（草稿） |
|---|---|---|
| 第一层 | 自动购买某个暗能量升级 | —— |
| 第二层 | —— | **自动购买无限升级 / 引擎等级 / 铸币**（按策略，而不是"买得起就买"） |
| 第三层 | —— | **条件自动化**：例如"过载因子 < 0.05 时自动大坍缩"、"ZPE 够下一对量子时优先买 X" |
| 附带 | —— | **每条 neko 等级给一点全局加成**（"可爱东西的加成"落在 `global` 金或 `dream` 虹） |

## 3. 草稿结构（等你改）

```
neko 等级（花梦想点，价格 ×3/级，来自"成就"而不是刷资源）
  ├─ 等级 1：自动购买「无限长河」之后——自动大坍缩（条件可调：按过载因子 / 按耗时上限）
  ├─ 等级 2：自动购买 ∞ 升级（按价格从低到高，和 infinity-sim 里那个贪心策略同源）
  ├─ 等级 3：自动购买 ZPE 引擎等级（买得起就买，但尊重软上限）
  ├─ 等级 5：自动购买「无限铸币」等级（**只在档位上限内**）
  ├─ 等级 8：条件策略可编辑（"过载 < X 收"、"耗时 ≥ Y 收"）
  └─ 每级附带：全局加成 ×(1 + 0.05×等级)  ← "来自某个可爱存在的加成"
```

设计上刻意**只有一条升级线**（neko 等级），而不是再加一堆条目 ——
梦想点数量有限，条目多了会变成"选不完的菜单"。

## 4. 三条必须遵守的约束（来自本项目的既有判据）

1. **不能绕过扣款**：自动购买必须走引擎里同一个 `buyXxx()`，
   （踩过的坑：`autoAcquire` 与手动点击曾双倍发放等级，见 `buyRepeatable` 的注释）。
2. **不能在 render 里做决策**：自动化只在 `tick` 里跑，UI 只读。
3. **日志要守关键节点规矩**：neko 自动买等级的日志必须走 `pushLevelLog()`，
   否则一帧能刷几百条（见 README「日志策略」）。

## 8. 可行性评估（我逐条取证后的结论）

### 8.1 结论一览

| 需求 | 可行性 | 依据 / 阻塞点 |
|---|---|---|
| 好感度（0 起、−100..+100、正向可超 100） | ✅ 直接做 | 纯状态字段 |
| 好感度 >25/50/75 → 全局加成 `^1.002/^1.005/^1.015` | ✅ 做，但**必须加 S 判据断言** | 实测 `S = 0.7263`；`^1.015` → `S_eff = 0.7372`；**红线 `1/S = 1.3769`**，余量充足 |
| 每 5 分钟波动 < 8 点（接入后 < 16 点） | ✅ 直接做 | 就是速率限制（用 `state.nekoLastTick` 计时） |
| 道具：免费猫条 / 棒棒糖（花物质）/ 猫爪（花 ZPE） | ⚠️ **定价有漏洞**，见 8.2 | "花光当前全部 X" 可被套利 |
| 左侧主控台新增标签页 + 聊天 | ✅ UI 可做；聊天**需要 SDK** | 左栏目前是资源卡 + 日志卡，加一张带小标签条的卡即可 |
| 日志暴露给 SDK 且不被任何重置重置 | 🟡 **一半已满足**，见 8.3 | 现已持久化且不被重置清空；但只有文本、上限 60 条、无订阅接口 |
| SDK 真实接入（猫娘控制好感度 / 替玩家自动化） | ❌ **需要 SDK 规格**，见 8.4 | 仓库里没有 SDK，也没有传输规格 |
| SDK 自动化**不消耗梦想点**、可代做**未解锁**的自动化 | ✅ 可做，但需要"阶段白名单 + 限流 + 幂等" | 项目踩过"自动化与手动双倍发放"的坑 |

### 8.2 硬问题 ①：「花光当前全部物质 / 全部 ZPE」不是真成本

- **棒棒糖**花"当前所有物质"：物质在**大坍缩时本来就要归零** → 玩家只要**在坍缩前买**，
  成本就是 0 → 等于**免费无限好感度**。
- **猫爪**花"所有 ZPE"：ZPE 会按当前速率自己长回来，而且**量子数量不受影响**
  （量子门槛只看 `log10(ZPE)` 的对数阶梯）→ 成本只是"等一会儿"，也接近免费。
- **危害评估（不致命但会毁掉设计意图）**：好感度门槛只到 75，白送 `^1.015`
  → `S_eff` 从 0.7263 到 0.7372，**不会崩**；但"三档奖励"会变成"开局十分钟就能拿满"。
- **三种修法**（任选其一，我推荐 A）：
  - **A（推荐）固定大额 + 冷却**：棒棒糖要 `1e250 物质`、猫爪要 `1e100 ZPE`，且同类道具 30 分钟内只能买一次；
  - **B 按比例消耗**：消耗当前物质/ZPE 的 50%（保留一半，避免"归零惩罚"太狠）；
  - **C 无成本但有硬冷却**：道具免费，但每件道具各自 30 分钟冷却（把"资源成本"换成"时间成本"）。

### 8.3 硬问题 ②：日志要"能被 SDK 读"，现在只有文本

现状（已取证）：
- `pushLog` 存 `{ t, text }`，**上限 `LOG_MAX = 60` 条**；
- `serialize` / `deserialize` **都保留 log**，`engine.js` 里**没有任何清 log 的动作**
  → 「不被任何重置重置」这条**基本已经满足**；
- 但 SDK 要读它只能做**中文字符串匹配**，非常脆；60 条也装不下历史。

建议改造（不依赖 SDK，可先做）：
1. 每条日志加 `kind`（`crunch` / `buy` / `milestone` / `quantum` / `system`）与 `data`（结构化数值），
   并加 **schema 版本号**（`state.logSchema = 1`）—— 将来 SDK 升级不用猜；
2. 给 SDK 一条**更长的环形缓冲**（如 2000 条，`logPanel` 仍只渲染 60 条）；
3. 提供**订阅接口**（`nekoBridge.onLog(cb)`），而不是让 SDK 轮询整个 state。

### 8.4 硬问题 ③：SDK 本身不在仓库里

我能做的：**适配层 + 契约 + 本地回退**。
- 适配层：`window.nekoBridge`（Electron preload 暴露）**或**本地 WebSocket；
  两种都支持也可以（浏览器版走 WS，打包版走 IPC）。
- 本地回退：未接入时，好感度由**道具**驱动（你说的"保持原状"），聊天页显示"未接入 project N.E.K.O."。
- 做不到（需要 SDK 方给规格）：真实聊天、**由猫娘控制好感度**、SDK 侧自动化。

需要 SDK 方给出：**传输方式**（preload IPC / 本地 WS / 两者）、**消息 schema**、
**鉴权**（本地端口要不要 token）、以及**它能改游戏状态的权限边界**。

### 8.5 SDK 自动化的安全边界（设计，不依赖 SDK）

1. **阶段白名单**：`neko.allowedStages(state)` 只放行玩家**已经到达**的阶段
   —— "替玩家自动化未解锁的自动化"指的是"自动化动作"，**不是**"越过阶段门槛"。
2. **只走现有 `buyXxx()`**：绝不自己写扣款（项目踩过 `autoAcquire` 与手动点击**双倍发放等级**的坑）。
3. **限流 + 幂等**：每 tick 最多 N 次动作；重复调用同一动作不叠加。
4. **断言**：`tools/neko-lab.mjs`（新）—— 白名单不许越界、不许双倍发放、不许绕过扣款、
   好感度加成的 `S × expMax < 0.95`。

### 8.7 要暴露给 SDK 的**只读资源**清单（用户要求）

原则：**只读、版本化、不暴露可写入口**（可写能力只走 8.5 的白名单动作 API）。

```js
nekoBridge.read() → {
  schema: 1,                       // 版本号，字段增删要 bump
  t: 1699999999999,                // 快照时间
  resources: {                     // ★ 关键资源（用户点名要）
    entropy, particle, matter, zpe, darkEnergy, quantum,
    infinityPoints, eternityPoints, dreamPoints,
  },
  rates: { entropy, particle, matter, zpe, darkEnergy, infinityPerHour },
  progress: {                      // 阶段与关键节点
    phaseTransmuterUnlocked, brokenInfinity, bigCrunchCount,
    quantumPairs, zpeMilestones: [...], deMilestones: [...],
    zpeEngine: { unlocked, level }, eternityCount,
  },
  multipliers: { global, dream, countFreq, de, zpe, overload },
  log: [ { t, kind, text, data } ],   // ★ 结构化日志（见 8.3），长期保留
}
```

- **长期暴露**：`log` 走更长的环形缓冲（如 2000 条）+ 结构化字段，并**不被任何重置清空**（已确认现状就保留）。
- **订阅**：除了一次性 `read()`，再给 `onLog(cb)` 与 `onTick(cb)`（节流到比如 1 秒一次），
  避免 SDK 轮询整个 state。
