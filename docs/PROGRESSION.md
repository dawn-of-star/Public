## 0. 骨架：**唯一的警戒值是「基本物质」**（用户定，2025）

用户原话：

> 要警戒的数值只有**基本物质**，而基本物质能换 IP，IP 换永恒点/EP
> （换言之我想的是：想引爆某个系统换取基本物质的推进）

### 0.1 这条骨架的含义

```
        ┌──────────── 被警戒的唯一变量（有硬顶）────────────┐
        │              基本物质（Matter）                    │
        │   硬顶 1e308.25 → 强制大坍缩 ｜ 过载拐点软上限      │
        └───────────────────┬───────────────────────────────┘
                            │ 大坍缩（深度收益）
                            ▼
                          无限点（IP）
                            │ 永恒（EP 公式同 AD）
                            ▼
                     永恒点（EP）→ ？（奖励待定）
```

- **物质是唯一的"警戒值"**：它是**有硬顶**的那一个（1e308.25 + 过载软上限），
  所以它天然是"进度货币"——其它系统跑多快都不怕，怕的是物质本身失控。
- **其它系统的职责 = 推动物质**：允许甚至鼓励某个子系统**引爆（runaway）**，
  但它的产出必须**汇入物质的推进**，而不是另开一条平行链。
- 链条是**单向**的：物质 → IP → EP。反过来不成立（IP 不该直接推物质？见 §0.3 的待定）。

### 0.3 ⚠️ 我们当前**链条断在哪**（重要）

按这条骨架检查现状，有两处**与用户意图不符**：

| 现状 | 为什么不符合骨架 |
|---|---|
| ① `ipDouble`（IP 收入 ×3/级）与**铸币**（IP 收入 ×2.5/级）都是 **IP → IP 的平行环** | 它们是 runaway，但产出**汇入 IP**，不是"推动物质" ✗ —— 骨架要求引爆的产出最终变成物质推进 |
| 深度收益 `floor((L/308.2547)²)` 在 308 阶附近**恒为 1**（缺口 G3） | 物质是警戒值、也是进度货币，可**"把物质推得更深"现在几乎不给 IP** ✗ 于是"推物质"这件事本身没有回报 |

**所以骨架一旦确立，G3 的方向就明确了**（不再是"要不要修"，而是"必须按这个方向修"）：

| 选项 | 做法 | 影响 |
|---|---|---|
| **A** | 让**深度收益随物质深度真的增长**（例如对超出 308.25 的部分给指数：`10^(k·(L−308.25))`） | 立刻让"推物质"有回报；不动铸币 |
| **B** | 让**铸币（或它的后继机制）喂物质**而不是喂 IP（例如「铸币等级 → 物质产出的指数/斜率」） | 最贴骨架；但铸币是"保留最终修改权"的设计，需要你拍板 |
| **C** | A + B 都做 | 链条最完整（引爆 → 物质 → IP → EP 单向贯通） |

> 另外这条骨架也回答了 G4（永恒奖励）：**奖励应当作用于"下一次把物质推起来"的能力**
> （而不是直接给物质），这样"永恒 → 更快到顶 → 更多 IP → 更多 EP"才是闭环。

### 0.4 AD 实读：它"动指数"的三个手法（`D:\game\AD-breaketernity-main`）

> 路径已更新到 `D:\game\AD-breaketernity-main`。以下**逐条实读**（不是凭记忆）。

**① 让产出的「log 的幂」大于 1 —— 这才是"动指数"**

`src/core/dimensions/antimatter-dimension.js`：

```js
let production = amount.times(this.multiplier).times(Tickspeed.perSecond);
...
if (production.gt(10)) {
  const log10 = production.max(1).log10();
  production = Decimal.pow10(Decimal.pow(log10, getAdjustedGlyphEffect("effarigantimatter")));
}
```

即 `产出 = 10^( log10(产出) ^ k )`，`k = effarigantimatter`（Effarig 符文效果）。
倍率页把它显示成"**额外指数**"：`pow(log10(baseProd), k − 1)`，且 `isActive: k > 1`。
**`k > 1` 时产出变成超指数** —— 这就是"引爆系统换物质推进"的引擎。

**② 把已有倍率整体取幂**（同文件 line 154 `multiplier.pow(glyphPowMultiplier × …)`；
line 69 `dilatedValueOf(multiplier.pow(glyphDilationPowMultiplier))`）
—— 等价于"把 log(倍率) 乘一个系数"，是同一招的另一种写法。

**③ ★ 关键：被硬顶的警戒值要继续给收益，得用「累计量」而不是「当前量」**

`src/core/secret-formula/infinity/break-infinity-upgrades.js`：

```js
totalAMMult:   effect: () => Decimal.pow(player.records.totalAntimatter.max(1).log10().add(1), 0.5),
currentAMMult: effect: () => Decimal.pow(Currency.antimatter.value.max(1).log10().add(1), 0.5),
```

两个升级：**一个按「累计反物质」的 `log^0.5`，一个按「当前反物质」的 `log^0.5`**。
反物质当前值被 JS 上限（1.79e308）**硬顶**，但**累计量一直在涨** ⇒ "推得久"这条路永远有回报。

### 0.5 ⇒ 因此我们的修法（待用户拍板）

**问题根源**：我们的深度收益只依赖**当前物质**（`(L/308.2547)²`），而物质有硬顶
⇒ 公式必然在天花板附近**变平**（实测恒为 1）。

| 选项 | 做法 | 与 AD 的对应 |
|---|---|---|
| **A′（推荐，最贴骨架）** | 记录**累计物质**（`totalMatterProduced`），深度收益改为 `log10(累计物质)^p` 形式 | = AD 的 `totalAMMult`（**用累计量绕过硬顶**） |
| **B′（真·动指数）** | 让某个系统的产出走 `10^(log10(prod)^k)`、`k > 1`（AD 手法 ①） | 需建模：`k>1` 会改曲线形状，必须先算 S 判据与到顶时间 |
| **C′** | A′ + B′：累计量负责"持续给"，指数负责"越推越快" | AD 后期正是两条叠着用 |

> 值得注意：我们**已经有一半**了 —— `infinityPointGain = (log10(M)/308.2547)^2`
> 本身就是"log 的幂"形式（AD 同源）；缺的是**换一个不被硬顶的输入量**（当前值 → 累计值）。

### 0.6 用户意向：**ZPE 引擎就是"动这个指数"的那台机器**

用户原话（2025）：

> 我希望真空零点能引擎 / ZPE 引擎就是**动这玩意**的东西，通过引擎加速…

也就是：**AD 手法 ①（`10^(log10(prod)^k)`，`k>1`）在我们要由 ZPE 引擎来提供**，
成为"把物质推起来"的那台引擎。

#### 现状：引擎**确实已经在动指数**，但落点与上限都不是你要的

| | 现状（`ZPE_ENGINE` ①） | 用户想要的（AD 手法 ① 的落点） |
|---|---|---|
| 动的是谁的指数 | **`zpeMultiplier` 的公式指数**：`(ZPE+1)^exp`，`exp = 0.02 + 0.03` | **产出的 log 的幂**：`产出 = 10^(log10(产出)^k)`，`k > 1` |
| 怎么影响物质 | 间接：`zpeMultiplier` → `effectiveTraps`（m4）+ ZPE 产出（v6）→ 物质产出（实测**杠杆 ≈ 1.95**，即倍率进两次） | 直接：指数作用在物质产出本身上 |
| 能到多大 | **很小**：`exp` 从 0.02 → 0.05，且 `expLevel=10`、`expPerLevel=0.002` ⇒ **第 25 级就吃满**；再经杠杆 ≈ ×28 物质产出 | 可随进度持续增长（AD 里 `k` 由符文/现实层继续抬） |
| 上限 | `expMax = +0.03`（硬编码）+ 引擎等级的价格软上限（1e308 点 → 211 级） | 需要新的上限策略（因为 `k>1` 本身就是形状变更） |

**所以这不是"从零加机制"，而是"把 ① 的落点搬对 + 放开它的上限"** —— 现有三条机制（①抬指数 ②产出 ×(`1+0.1lv`)² ③吃计数频率）里，① 就是这台机器，只是它现在被钉在一个小范围里，且作用的是倍率公式而不是产出本身。

#### 三个选项（都要先建模再实现）

| 选项 | 做法 | 风险 / 需要先算的东西 |
|---|---|---|
| **Z1（搬落点）** | ① 直接抬**物质产出**的指数：`matterRate` 里加 `10^(log10(base)^k)`，`k` 由引擎等级给（1 → 1.0x） | 物质在**环**上 ⇒ 必须重算 S 判据（现 0.7263）与 24h 到顶时间（`crunch-speed-lab`） |
| **Z2（放开 ① 的上限）** | 保留 ① 的落点（`zpeMultiplier` 的指数），但把 `expMax` 从 `+0.03` 改成随等级/里程碑增长 | 会推 `a_worst = (0.02+expMax) × 1.95`（现 0.097，红线 0.5）⇒ 必须先算 a 的余量 |
| **Z3（新增第四条机制）** | 引擎等级 → **物质产出指数**，与前三条并列（不改 ① 的语义，避免歧义） | 与 Z1 数值上等价，但**落点更清楚**（"引擎有一条机制专门管物质指数"）；同样要算 S 与到顶时间 |

> ⚠️ 两条既有判据仍然适用：
> **(a)** 引擎等级本身**必须保持极强软上限**（用户早前指定：影响永恒阶段的东西不许 runaway）——
> 所以"引擎动指数"要设计成**有界但持续变强**，不能变成无限 runaway；
> **(b)** "动指数"= **改曲线形状**，改之前必须先算 S 判据与到顶时间，不能直接改代码。

## 4. 设计原则（沿用项目既有判据，别再重复踩）

1. **形状 vs 高度**：加固定倍率只平移高度；改曲线形式才动形状。加"新的数量级来源"前必须先想清是哪一类。
2. **环增益判据**：任何进环（同时喂熵与物质）的东西，都要让 `Σ log(m)/log(r) < 1`。当前 **0.7263**。
3. **节流阀必须卡住每一个同侧循环**：只卡一个没用（模型实测：只卡铸币上限时结果完全不变）。
4. **闸门之间禁止加法耦合**：`上限 = 引擎等级 + 档位×增量` 这种写法会让一个循环把另一个的闸门顶开。
5. **影响永恒阶段的东西必须有极强软上限**（用户指定）：分轴价格段 / 效果硬封顶，二选一。
6. **显示 == 实发**：界面显示的收益必须与引擎实际发放走**同一个函数**（踩过：铸币倍率只在界面生效）。
7. **一次性升级必须登记"已购"**：否则会被无限次重复购买（踩过：直接导致 IP 池永远停在个位数）。
8. **每个机制都要有断言 + 文档**：没有断言与文档的机制视为没做完。

## 7. 数学推导：**没有 R，量子怎么把物质推到第一次大坍缩**（2025）

> 与 §5.2 / `tools/*lab.mjs` 无关的**独立推导**（用户要求：排除已有模型，纯公式）。

### 7.1 两条微分方程

```
① 粒子线： dP/dt = c₀ · G(t)，  G(t) = 10^(b·t)      （b = 粒子增幅速率，由量子给）
② 物质线： dM/dt = k · P(t)                          （k = matterCoeff）
```

积分：

```
P(t) = P₀ + (c₀/(b·ln10)) · (10^(b·t) − 1)
M(t) = M₀ + (k·c₀/(b·ln10)) · [ 10^(b·t)/(b·ln10) − t ]
t 大时： M(t) ≈ k·c₀·10^(b·t) / (b·ln10)²
```

### 7.2 结论：`log10(物质)` 是时间的**线性函数**，斜率就是 `b`

```
log10 M(t) ≈ log10( k·c₀/(b·ln10)² ) + b·t
                                  └ 常数 ┘   └ 斜率 b ┘
⇒ 撞 1e308.2547 的时刻：  t = 308.2547 / b
```

**代入标定值**：`b = b0·(1+√q/10)·qm1`，`b0 = 0.003755`、`q ≈ 30`
⇒ `b ≈ 0.00639` ⇒ `t = 308.25/0.00639 = 48,200 秒 = 13.39 h` ✓（= ×1.75 标尺目标 ✓ 自洽）

### 7.3 必要性：**常数倍率到不了 inf**

```
若 G = 常数（普通倍率）⇒ P = c₀·t ⇒ M ∝ t² ⇒ log10 M = 2·log10 t + 常数
要 308 阶 ⇒ log10 t = 154 ⇒ t = 1e154 秒 ✗✗
⇒ G **必须随时间增长**（这正是 R 当年存在的理由，也是 `b` 现在必须时变的原因）
```

### 7.4 实测比推导快 1.27× —— 推导自己解释了它

```
q 在**一轮之内**也在涨（ZPE 门槛每次 ×20 ⇒ q ≈ 2·log₂₀(ZPE)）
⇒ b(t) = b0·(1+√q(t)/10) 随时间增长 ⇒ 真实是 dL/dt = b(t) > b(0)
⇒ 实测 10.52h < 用起始 b 反解的 13.39h ✓ 完全自洽
```

### 7.5 量纲陷阱（工具里常被搞错）

`b` 的单位是 **阶/秒**（log-matter 的斜率），**不是**"倍率/秒" ✗
它与 R（0.147 阶/秒）**同量纲** ⇒ 所以 `crunch-speed-lab` 那条"耗时 ∝ 1/速率"**对 `b` 依然成立** ✓
